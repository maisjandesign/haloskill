# Project documents and publishing

## One project, one maintained record

Default to a Project Overview parent with four child sections: Sales to Delivery Handoff, Scope & Deliverables, Delivery Plan, Project Tracker. Use existing equivalent sections rather than creating a competing workspace. Scale the structure down for a focused update or a small engagement. Project Setup owns the overview, handoff, scope and tracker; Roadmap to Timeline owns the dated plan. Start produces the opening readiness assessment, not an additional route report.

Keep detailed scope in the deliverable inventory, questions/decisions/risks in the tracker and dates in the delivery plan. The overview summarizes their implications without repeating all their rows. Cross-reference stable IDs and descriptive links. When presenting a preview, identify it as a draft rather than silently replacing an approved baseline.

## Ready-to-use writing

Default to English unless the user specifies another language. Write finished project prose with meaningful headings and concise tables; remove authoring prompts, unused fields and template placeholders. Explicitly state missing consequential information instead of filling it with guesses. A proposed role is different from an assigned person. Separate draft, team-reviewed and client-approved status.

Do not mention AI, skills, commands, routing, source repositories or generation mechanics in project-facing output. This excludes production commentary, not relevant facts about the client's product. Keep execution limitations and technical logs in the conversation or working files.

Use real destination URLs when available, not local relative paths in copy-and-paste documents. Make each page understandable on its own; links supplement rather than replace a written answer. Before publication, check title, source/version, status, ownership gaps, next actions and references. Do not carry private client facts or dates into reusable templates.

## Commercial handoff and review rules

Sales handoff is an internal section. Keep commercial assessments and negotiation context separate from client-facing scope. A page title saying Internal does not restrict access: inspect inherited sharing when publishing sensitive material, and use an appropriate authorized destination. Do not change access or share externally just to match the template.

Capture observable communication preferences, timezone, availability and decision behavior. Do not infer working behavior from nationality or other demographic traits. For materials shown during sales, distinguish what the client liked about message, visual style or execution from what was actually promised.

Define who consolidates feedback, who approves, which artifact/version is reviewed, the agreed response window and revision allowance. Leave unknown limits pending. A delayed response is not approval. Reopening accepted work becomes a proposed change with its cost/date/scope impact and a recorded decision.

## Native workspace, when requested

Use the actual available connector or computer-use interface. Read the intended destination before writing. For a new workspace create the parent and real child pages; preserve existing content and use stable page/database/item identities on repeat runs.

Use native project properties for key status/owner/date fields where supported, readable native tables for scope and commercial summaries, and native databases for live tasks and schedules. Reuse relevant existing databases through linked views instead of copying task rows. A static table is acceptable for a review document, but describe it accurately; it is not a connected tracker or an automated relationship.

A task board groups by workflow status; detailed blocking reasons belong on tasks rather than becoming a separate column for every issue. Use table views for open questions, decisions and risks when useful. Create native relations only where they help maintain the project; do not imply that text IDs are relations or automations.

Store tasks with ID, owner, status, dependencies, acceptance evidence and target date. Questions need a decision owner, next action and needed-by date or gate. Schedule rows use native dates and explicit work/review/milestone types; follow Roadmap to Timeline for calendar verification. Expose absent owners visibly rather than assigning people without evidence.

Check the rendered pages: readable table widths, clear status callouts, working child-page navigation, correct links, populated board views and the timeline's project date window. Report actual limitations. If publishing is unavailable or unrequested, deliver self-contained documents and distinguish them from an implemented workspace.
