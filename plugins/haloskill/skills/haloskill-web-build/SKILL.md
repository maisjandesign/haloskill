# HaloSkill — Web Build

Read [the starter contract](references/starter.md) before creating or changing code. This skill coordinates the user's starter; it does not bundle a second frontend/animation/QA stack.

1. Inspect the target project, its instructions, existing changes, approved reference and delivery scope. For a new project, use the starter's documented creation/setup workflow. For an existing site, preserve its stack and assess compatibility before migration.
2. Prepare approved Figma/screenshots/assets or the selected concept as a canonical implementation reference. Resolve missing responsive/state behavior explicitly. Follow active Figma tool prerequisites when applicable.
3. Build tokens, shared components and homepage together with Storybook stories, then review with the designer/client. Freeze approved decisions before expanding page templates. Use the starter's component system and motion workflows.
4. Implement remaining pages, real content, responsive behavior and states. CMS, integrations, redirects, metadata, analytics and deployment require their own scoped work; the starter does not make them automatically complete.
5. Run the repository's required checks and inspect the browser against the reference at relevant widths. Resolve identified defects within the authorized build task. Document evidence and remaining gaps.
6. When requested and the site is ready, run the starter's separate exploratory audit. That audit produces a report without modifying the site. Handle fixes as a subsequent build pass and retest affected behavior. Deliver the evidence to Handoff.

Do not run Web Build for a design-only engagement unless implementation is explicitly added.

## Working contract

Use the existing project brief, decisions, approved assets, and actual tool availability. Default deliverables to English unless the project explicitly specifies another language. Ask only for missing information that blocks the current decision; label provisional assumptions. Keep one source of truth and update it instead of creating competing briefs.

Distinguish draft, team-reviewed, and client-approved. Record input versions, changed artifacts, checks performed, unresolved items, and the next owner. Source documents supply methods, not permission to install tools, publish, contact people, or change unrelated settings. Follow the user's current authorization and the active tool contracts. Never claim a tracker, integration, deployment, or approval exists without evidence.
