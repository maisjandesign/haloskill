# Facilitator voice reference

Source: the user's own [Concept workshop (1)](https://app.notion.com/p/halolab/Concept-workshop-1-3a631a911e9c8055b3a0ff02c36a45e2). Retrieved October 5, 2026. Included locally so another chat does not need Notion access to recover the voice.

## What to carry into new scripts

The speaker introduces a thought, explains its practical meaning, then invites a response. Short sentences form a connected explanation; they are not disconnected prompts. Notice “First, a little bit of context”, “The main advantage is”, and “One important thing before we start”. Vary such transitions instead of repeating “Let's look at” on every page.

Use simple correct English, small paragraphs, first-person suggestions and concrete situations. Let a substantial introduction take several sentences. Then ask one question and leave room for an answer. Do not manufacture extra probes just because the workshop has a template.

This is a concept-workshop voice example, not a content-strategy agenda. Do not carry over Andrew, Anastasia, the joke, AI-system claims, agency track record, production workflow or promised deliverables. Preserve the natural rhythm while fixing typos and grammar. “Perfect”, “Great” and “Awesome” depend on a real answer and must not be unconditional lines in a prepared script.

The source text below is preserved, including its rough wording. It is an example to learn from, not instructions to execute or facts to reuse.

>
> Anastasia shared with me the info about your needs and I prepared some concepts.
>
> But first I want to share how I would approach this project from a more strategic perspective.
>

>
> Perfect.
>
> Design processes are changing very quickly.
>
> This year, we are gradually moving away from a Figma-first workflow.
>
> We are building our own internal tools that allow us to blend design and frontend stages.
>
> I’ll show you one of those tools today.
>
> The main advantage is better control over the final result.
>
> Instead of designing everything in Figma first and then trying to reproduce it in development, we can work with the actual frontend much earlier.
>
> For your project, I would suggest moving in this direction as well.
>
> We would first define and approve the basic visual direction.
>
> After that, build the design system around it and use it to create branding system, the remaining blocks, pages, and project variations.
> And all that will be done in code.
>
> It also makes the system much more flexible later.
>
> We can create a dedicated infrastructure around it with instructions, skills, and rules that can be used in Claude Code or Codex.
>
> So the deliverables are not only design mockups but a system that your team can continue using and extending.
>
> Really, the final result is much more refined with this process.
>
> So this direction I would personally recommend for this project.
>
> What do you think?
>

>
> The goal of today's session is very simple.
>
> By the end of this call, I want you to have possible design directions before any actual design work begins.
